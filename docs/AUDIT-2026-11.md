Each finding has an ID (H = high, M = medium, L = low) so a follow-up task can say "fix H2". Line numbers refer to `25832fa`.

## 2. High severity

### H1 — 3D Observatory stuck on "Loading observatory…" when the font CDN is unreachable
- **Where:** `src/components/canvas/ObservatoryScene.tsx:1092` (`<Text>` without a `font` prop). drei's `Text` calls `suspend(() => new Promise(res => preloadFont({ font, characters }, res)))`. With no `font`, troika-three-text 0.52 resolves glyphs through `@unicode-font-resolver`, fetching JSON and woff files from `https://cdn.jsdelivr.net/gh/lojjic/unicode-font-resolver@v1.0.1/...`. When that fetch fails, the promise never resolves.
- **Evidence:** in both the production build and the dev build, the 3D panel still showed the spinner after 45 s, both with the host blocked and with it returning 404. Only the two 2D canvases were visible. Page error: `Failed to fetch` (unhandled). Screenshots were taken at 1440×900 and 1280×720.
- **Impact:** offline or firewalled classrooms (the program's stated audience), school proxies, and regions where jsdelivr is blocked or slow get no 3D at all. The default layout is split view, so a third of the screen is a spinner.
- **Fix:**
  1. Ship a font in `public/fonts/` and pass `font="/fonts/<file>.woff"` plus `characters="NESW…"` to every `<Text>`. Alternatively, replace the labels with canvas-texture sprites.
  2. Wrap the lazy `ObservatoryScene` in its **own** `ErrorBoundary` and a Suspense that times out to a static fallback. Today the only boundary is the root one in `main.tsx`, so any WebGL failure (context creation refused, context lost on a low-memory tablet) takes down the 2D eyepiece as well. This is a plausible source of the "intermittent crashes" reported before Phase 65/66.
  3. Self-host the four photographic textures (about 0.76 MB) in `public/textures/` instead of hot-linking `upload.wikimedia.org` (`src/engine/assetLoader.ts:32-43`). They already degrade gracefully, but offline sessions never get the photos. The dead `surfaceTextureUrl: '/textures/*.jpg'` fields in `src/data/bookContent.ts` could then point at real files.

### H2 — The finder has two independent misalignment systems; "aligned" ignores the real one
- **Where:**
  - Legacy pixel offset: `src/store/useAlignmentStore.ts:18-19` (starts at 45, −30 px, and `setOffsets` is never called anywhere). It is moved by the round thumbscrew buttons.
  - Angular error in degrees: `finderscopeError` in `useTelescopeStore`, moved by the ▲▼◀▶ buttons and by Scramble.
  - Both shift the finder view: `src/engine/skyRenderer.ts:976-988`, `LiveViewPanel.tsx:447-448`.
  - `checkAlignment` (`useAlignmentStore.ts:46`) tests **only the pixel offset**. It drives the green crosshair, the `first_alignment` achievement, and the Saturn Recon step `finderscope_spire` (`src/engine/missionEngine.ts:485-486`).
- **Evidence (live, `scripts/audit/live-bugs.cjs`):**
  - T1: Fun mode ("finder pinned perfect") still has the 45, −30 px offset, so the finder is **1.62° off**. The screenshot shows the tower off-centre while the panel reads "Δalt 0.00° · Δaz 0.00° · TARGET CENTERED".
  - T3: after Scramble (Δalt −1.69°, Δaz +1.35°) with the pixel offset zeroed, `isAligned` is `true`. Green crosshair, mission passes, and the finder is still 2.2° off.
- **Fix:** keep one model, in degrees. Compute "aligned" from the combined angular axis error (`finderscopeError` + pixel offset ÷ px-per-degree) against a threshold in degrees. Reset or remove the legacy pixel offset (Fun mode and Scramble must clear it). Ideally retire the pixel thumbscrews, or make them drive `finderscopeError`.

### H3 — Guided-mission steps and lesson completion wait for unrelated state changes
- **Where:** `src/App.tsx:609-674`. One `useEffect` runs `evaluateLessonCompletion()` and `evaluateMissionProgress()`, but its dependency list has no alignment state, no `completedModules`, no `achievements`.
  - `finderscope_spire` waits on `alignment.isAligned`.
  - `dobsonian_saturn` waits on `completedModules`.
  - Lessons wait on achievements and modules.
  - Rank missions are covered by a 500 ms poll (`App.tsx:684-691`); guided missions are not.
- **Evidence (T2):** after the finder became aligned, the step index stayed the same for 3 s. It advanced only after an unrelated focuser nudge.
- **Fix:** subscribe the evaluator to the stores it reads (`useAlignmentStore` `isAligned`, progress `completedModules` and `achievements`). Alternatively run it from the existing 500 ms poll, or from store subscriptions outside React.

### H4 — Moon phase terminator drawn in the wrong direction
- **Where:** `src/engine/skyRenderer.ts:836-844`: `brightLimbRad = Math.atan2(-dAlt, dAz) + parallacticAngleRad`. Two errors:
  1. Raw altitude/azimuth differences are not the direction toward the Sun on the sphere. The Sun is often 60–180° away.
  2. The parallactic angle is added again. `eraseLunarPhaseShadow` works in screen space, separately from the texture rotation, so `+q` mis-rotates the terminator by `q`.
- **Evidence:** `scripts/audit/astro-accuracy.ts` §2, 833 samples with the Moon above 10°. Mean error **35.5°**, max 179.8°. Without the `+q` term the error is still up to 130°.
- **Fix:** use the great-circle bearing in the same screen basis the renderer uses (x = increasing azimuth, y = up):
  ```ts
  // m, s: unit ENU vectors of Moon and Sun; t = s − (s·m)m
  // right = (cos az, −sin az, 0), up = (−sin alt sin az, −sin alt cos az, cos alt) at the Moon
  brightLimbRad = Math.atan2(-dot(t, up), dot(t, right)); // no + parallactic angle
  ```
  The probe already contains this computation. Keep the texture's own `parallacticRad` rotation as it is.

### H5 — Astrophotography captures don't check the physical state; the tracking lock is a fake motor
- **Where:** `src/components/liveview/LiveViewPanel.tsx:1093-1182`. Grading uses only focus and the exposure settings.
  - No check of `isDustCapOn`, the solar filter, whether the target is above the horizon, daylight visibility, or whether it is actually in the field.
  - "Mount Tracking Lock" is the separate flag `isAstroTrackingLocked` (`useTelescopeStore.ts:365, 873-875`). It never engages the sidereal motor, and the motor being on doesn't count.
  - The Orion mission tells the student to put the cap on, take darks, then "Capture a final graded image!" (`missionEngine.ts:122`).
- **Evidence (T4):** with the dust cap ON, the motor OFF and the "lock" ON, a capture produced a `DSO Stack` logbook entry noted "Tracking: ON". It got grade F only because the focus was off. The `dso_stack` mission step (`missionEngine.ts:557-563`) accepts any non-trailed stack, so that capture would have passed.
- **Fix:**
  - Refuse or zero-grade a capture when the cap is on, the view is blacked out, or the target is not inside the field and visible.
  - Drive trailing from `isTrackingMotorOn`, or make the lock button toggle the motor.
  - Rewrite the Orion step 4 text so the cap comes off before the final lights.
  - Also fix:
    - `magnification: 1` in both entries (`:1118`, `:1167`).
    - "Adjust the focuser knob to exactly 50" (`:1104`, `:1154`). Perfect focus is 39–80 depending on eyepiece and Barlow; the 25 mm is at 60.
    - The `SNR … dB` label (`:828`). It is a linear ratio, not decibels.

### H6 — A mission that cannot be completed at default settings
- **Where:** `src/data/missions.ts:385-428` (`rank2_empty_magnification`) needs a Barlow, ≥ 120× and below the seeing ceiling (150× at seeing 3).
- **Evidence:** `scripts/audit/mission-feasibility.ts` tried every built-in scope × eyepiece × Barlow × seeing combination.
  - Empty Magnification: **impossible at seeing 3–5**. The student can only finish it by dragging the "weather" slider to 2. That is the opposite of the lesson ("the sky sets the ceiling").
  - Also impossible: Wandering Star and Paper Tube at seeing 5, and the Capstone at seeing ≥ 4 (no Saturn configuration fits).
- **Fix:** derive the target from the ceiling (for example "≥ 80 % of tonight's ceiling with the Barlow in"). Or add a 15–18 mm eyepiece (the Dob at 2400 mm / 16 mm = 150×). Or relax the threshold to ≥ 100×.

### H7 — The mount can point underground, and the eyepiece pretends it can't
- **Where:** `setTarget` writes the raw ephemeris altitude (`useTelescopeStore.ts:587`). So do time shifts with the motor on (`pointingAfterTimeShift`) and site changes. `setPointing` clamps to ≥ 0° (`:627`), so the first nudge jumps the tube. At startup the tube aims at the Moon (`:81`, `:1001`), which is below the horizon about half the time. The toast claims "mount parked at the horizon stop" (`App.tsx:816`). Only the 3D rig clamps visually.
- **Evidence (T5):** GoTo to M42 at midday: `pointingAlt = −33.9°`. The 10:30 AM screenshots show the default target "The Moon, −18°, Below Horizon", and the eyepiece shows **plain blue sky** while looking 18° into the ground. The finder panel reads "TARGET CENTERED — SCREWS UNLOCKED", so a student can align the finder on an invisible object.
- **Fix:** pick one convention. Either clamp GoTo at 0° with a "below horizon" refusal (what real hand controllers do), or render ground below 0° in both feeds. Don't unlock alignment, or count mission success, on a target below the horizon. At startup, choose a default target that is actually up, or don't auto-aim.

## 3. Medium severity

### Sky physics and accuracy

**M1 — On equatorial mounts the stars still rotate.** All layers are projected in an alt-az frame (`skyRenderer.ts:205-219`, "zenith up") for every mount type, and EQ mounts skip only the glyph rotation (`:773`). On the SCT the star pattern around tracked Saturn turns **about 64° in 3 h** (probe §3), which is about 64° in 3 real minutes at 60×, while the rings stay fixed to the screen. The README's lesson ("switch to the SCT and the view stops rotating") is half true, and stars and glyphs disagree.
*Fix:* for `!isAltAzMount`, rotate the sky layer by −q(pointing) about the canvas centre (one `ctx.rotate` per frame), so the frame is north-up and both stars and glyphs stay put.

**M2 — Galilean moons don't match the sky.** The `meanLongitudeJ2000Deg` values (`ephemerisMath.ts:614-619`) are Lieske E5 mean longitudes at epoch **JD 2443000.5 (1976)**, used as J2000. The Earth–Jupiter geometry is also missing.
*Probe §1:* errors up to the full orbit radius against Meeus ch. 44. Callisto is wrong by up to 51 R_J with the sign flipped, and moons appear on the wrong side.
*Fix:* Meeus ch. 44 low-accuracy method (about 40 lines, already in the probe; good to a fraction of R_J). The README currently promises a "live ephemeris".

**M3 — Planets are frozen.** Jupiter (RA 4.6h, "2024–25 snapshot") and Saturn (23.67h) are static (`bookContent.ts:43-81`). Against JPL Keplerian elements (probe §4):
- Jupiter is 74° off today (it is really in Leo/Cancer, a morning object).
- Saturn is 16–30° off and shown in the evening sky in Mar 2027, when it is really 33° from the Sun.

Real-time sessions show planets that aren't there, and the "go outside and find it" transfer breaks.
*Fix:* JPL "Approximate Positions of the Planets" (about 60 lines, ±arcminutes 1800–2050, in the probe). If a guaranteed winter Jupiter is wanted for lessons, make it an explicit "classroom sky" option.

**M4 — No precession.** The Sun and Moon series are referred to the equinox of date, while the stars, M42 and the planets use J2000 with the same LST. In 2026 the Moon is about 0.37° (0.7 lunar diameters) out of place against the stars. At 1610 (Galileo, via the Time Machine) it is about 5.4°, close to the finder's whole field. The code carefully adds GMST T² terms (22″ in 1600) but omits 5° of precession.
*Fix:* precess catalog vectors with Meeus ch. 21 (one rotation matrix per frame), or carry the Sun and Moon in J2000.

**M13 — Solar safety model simplifications that teach the wrong reflex.**
- The main-tube dust cap and solar filter suppress the hazard for the **finder** too (`rulesEngine.ts:93, 110`). The standard rule is "cap or remove the finder when solar observing", and a finder-only exposure is exactly the accident to teach.
- The main-feed flash uses the 4° finder-sized radius (`skyGeometry.ts:225`), so the main eyepiece flashes with the Sun outside its ~1° field.

*Fix:* separate finder cap/filter state; use radius = main FOV/2 + 0.27° + a margin for the main feed (keep the pre-warning).

### 3D observatory

**M5 — The German equatorial rig refuses half the sky.** `ObservatoryScene.tsx:907`: `hourAngle > 180°` means "danger". That is the entire eastern sky, every rising object. The rig clamps to the meridian (the 3D tube no longer points where the eyepiece looks) and a flashing red "EQ Mount Collision Imminent (Meridian Flip Required)" banner appears (`App.tsx:1403-1409`) with no flip available.
*Fix:* model pier side. For eastern targets use HA′ = HA − 180°, Dec′ = 180° − Dec (OTA on the west side, counterweight down). Warn only when tracking *past* the flip limit.

**M6 — Azimuth spins the long way round.** `THREE.MathUtils.damp` on raw radians (`ObservatoryScene.tsx:321-326`, and the HA damp at `:934`). Crossing north (359° → 1°) swings the rocker 358°.
*Fix:* damp the shortest signed angle delta.

**M7 — The 3D scene renders 60 fps forever.** `<Canvas>` (`:1349`) has no `frameloop` prop, so it uses `'always'`, with `meshPhysicalMaterial` transmission (an extra scene pass for the glass), clearcoat, PMREM and a 2048² shadow map. This is in the **default split view**, and runs even when nothing moves. The 2D feeds idle at 5 fps; the 3D scene doesn't. `isLowPerformanceDevice` is detected and persisted but changes nothing, and `showHighPerfToast` is never set to true.
*Fix:* `frameloop="demand"` plus `invalidate()` on pointing, clock (sky dome) and damping-in-progress. Plain standard material for the glass. Default to Eyepiece view, or a reduced 3D quality, on low-end devices.

**L8 — Stale shadow after GoTo.** The shadow map refreshes only on store pointing writes (`:1260-1270`), but the tube keeps damping for 1–2 s afterwards.

### Performance and bundling

**M8 — Lazy 3D is not actually lazy.** In the build, the `three` chunk starts with **React itself**. The entry imports React from it (`import {…} from "./three-*.js"` plus `<link rel="modulepreload" href="/assets/three-*.js">`), so 1 MB (287 KB gz) of three.js is fetched and parsed before first paint in every view. Combined with split view being the default, the Phase 59 split currently saves nothing.
*Fix:* in `vite.config.ts` `manualChunks`, send `react|react-dom|scheduler` to a `react` chunk, or use rolldown `advancedChunks` groups with priority. Then make Eyepiece view the default on first load or on low-end devices.

**L5 — Worst-case offscreen memory.**
- M42 composite: up to 2048² (16 MB) × 8 LRU entries (`targetGlyphs.ts:765-796`).
- Disk sprites: 12 × up to about 4 MB.
- The M42 cache key includes the blur, so focusing at high power re-bakes heavy filter passes.
- When the composite hits the 2048 cap the image is cropped from the top-left, so the nebula core shifts off-centre.

*Fix:* key on size only and apply the blur at blit time, cap total cache bytes, and centre the crop.

### UI, data and localisation

**M9 — Layout breaks at classroom resolutions.**
- At 1280×720 and 768×1024, split view clips both eyepiece circles and the finder controls.
- The top nav cuts off About and Settings with no scroll, so Settings is unreachable on a portrait iPad.
- The instructor HUD covers the telemetry panel at 1440×900.

*Fix:* overflow menu for the nav. Stack the two feeds vertically below about 1440 px wide, or auto-switch to Eyepiece view. Give the HUD a default position away from the telemetry panel.

**M10 — Two tabs lose data.** Each tab persists its own snapshot, so the last writer wins.
*Evidence (T6):* tab A logged an entry, tab B unlocked an achievement, and tab A's entry was gone from storage.
*Fix:* listen for `storage` events and call `useProgressStore.persist.rehydrate()`, or merge the logbook on write (union by id), or use `BroadcastChannel`.

**M11 — Hindi mode is partial, including the safety warning.**
- `InstructorVoiceBox.tsx:236` renders `response.message.text` verbatim.
- All rules-engine messages, `INSTRUCTOR_STRINGS` (including "SAFETY OVERRIDE! Unfiltered sunlight…"), mission texts, toasts, the EQ banner and the canvas HUD text are English-only.

*Fix:* emit message ids or keys and translate at render time. Translate the safety strings first.

**M12 — Clock and Time Machine use the browser's time zone, not the site's.** `TelemetryPanel.tsx:24-28, 255`; `App.tsx:851`. Switch the site to Sydney and the clock still shows India time, so "observe at 9 PM in Sydney" lands at mid-afternoon there.
*Fix:* store an IANA zone per city, format with `Intl.DateTimeFormat({ timeZone })`, and parse the picker in that zone.

**M14 — Missions promise checks that don't exist.**
- *Moon Diary:* "Repeat on at least 4 more nights… the Logbook is watching" is not implemented (no code reads 5 entries over ≥ 5 dates).
- *Capstone:* "The Logbook completes the mission when all three entries exist" is not implemented.
- *Orion step 3:* "≥ 10 subs, ≥ 30 s, SNR > 15" is not enforced; any non-trailed stack passes.
- *Saturn Recon step 3:* passes on *any* past completion of the tracker, with any target and from any session.
- *Rank missions:* none checks that the target is above the horizon, in daylight-visible conditions, or in the field, except the star-hop.

**M15 — Lucky-imaging model has no trade-off.** `calculatePlanetarySharpness` (`astroMath.ts`) is monotone: keeping fewer frames is always better, with no noise cost. Add an SNR ∝ √(frames kept) term so there is a real optimum near 5–20 %.
